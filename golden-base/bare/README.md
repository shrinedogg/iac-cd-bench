# golden-base/bare

The no-tooling control arm: `scenario/SPEC.md` implemented as raw,
hand-authored Kubernetes manifests applied with plain `kubectl apply -f`.
No Flux, no kustomize, no overlays, no rendering pipeline, no state.

`dev/` and `prod/` are two independent, fully-written-out directories, not
a base plus a patch. Anything that differs between environments (node
count, instance type, DB sizing, IAM trust policy, bucket replication) is
duplicated by hand rather than expressed once and overlaid. That
duplication is the arm's point: it's the cost `golden-base/knr-ops`'s
kustomize overlays buy back.

Resource kinds mirror `golden-base/knr-ops` where knr-ops's own equivalent
exists (CAPI/CAPA cluster objects); where knr-ops uses an Upbound/Terraform-
flavored Crossplane provider (`s3.aws.upbound.io`, `rds.aws.upbound.io`,
`iam.aws.upbound.io`), this arm uses the AWS Controllers for Kubernetes
(ACK) CRDs instead (`s3.services.k8s.aws`, `rds.services.k8s.aws`,
`iam.services.k8s.aws`), per this issue's brief.

## Secret handling

SPEC's acceptance criteria require the DB connection secret to "never be
stored in plaintext in Git; encrypted at rest via stack-native mechanism."
Every other golden achieves this with real machinery: knr-ops with
SOPS-encrypted values Flux decrypts at reconcile time, Crossplane with a
SecretStore/ProviderSecret, Terraform/Pulumi with their native secret
config types. `bare` has none of that - no operator, no CLI plugin, no
rendering step runs between this repo and `kubectl apply`.

So `dev/db-secret.yaml` and `prod/db-secret.yaml` are committed as **stub**
Secrets: a plain `v1/Secret` whose `password` field is a literal, obviously-
fake placeholder (`REPLACE_OUT_OF_BAND_NEVER_COMMIT_REAL_VALUE`), tagged
with `bare.golden/placeholder: "true"`, and preceded by a comment
explaining that the real value is supplied out-of-band immediately before
`kubectl apply` - e.g. `kubectl create secret ... --dry-run=client -o yaml
| kubectl apply -f -`, or generated by whatever CI/bootstrap process runs
this manifest set. The `DBInstance.spec.masterUserPassword` field
references this Secret by name/namespace/key rather than embedding a value.

This was chosen over the alternative RDS supports natively -
`manageMasterUserPassword: true`, which has AWS Secrets Manager generate
and own the credential entirely, with no Kubernetes Secret involved at all.
That option is arguably the *better* real-world choice for a from-scratch
bare deployment, but it was rejected here specifically because it sidesteps
rather than demonstrates the constraint every other golden has to solve:
"a secret reference lives in Git, the value doesn't." The stub-Secret
pattern keeps `bare` comparable to the other arms on that specific
acceptance criterion instead of opting out of it.

## Known gaps / things that can't be expressed cleanly in a bare manifest

These are candidate findings for the arm comparison, not bugs to fix here
(scope is `golden-base/bare/` content only - task/stack wiring is #38/#39):

- **IAM "programmatic access" has no CRD.** ACK's `iam-controller` exposes
  `Role`, `Policy`, `User`, `InstanceProfile`, `OpenIDConnectProvider`, and
  `ServiceLinkedRole` - there is no `AccessKey` kind. SPEC's dev-column IAM
  requirement ("IAM user + role ... programmatic access") can be satisfied
  for the user/role objects themselves, but the actual access key pair
  can't be expressed as a manifest in ACK at all; it has to be created
  out-of-band (`aws iam create-access-key`) the same way the DB secret is
  handled. This is very likely *why* knr-ops uses the Upbound provider
  instead of ACK - Upbound's `iam.aws.upbound.io/AccessKey` kind exists
  precisely where ACK has a gap.
- **IRSA role ARNs aren't known at apply time.** `prod/app.yaml`'s
  ServiceAccount needs `eks.amazonaws.com/role-arn` pointing at the Role
  ACK creates in `prod/iam.yaml`, but that ARN only exists in the Role's
  `.status` after ACK reconciles it - it can't be filled in when the
  manifest is authored. A templating/rendering pipeline (or Crossplane's
  patch-and-transform, or a two-phase apply) can wire status back into a
  sibling resource's spec; plain `kubectl apply -f` cannot, so the
  annotation is left as a documented placeholder for an operator to patch
  by hand post-creation. Same shape of problem for the OIDC provider
  ARN/account ID placeholders in `prod/iam.yaml`'s trust policy.
- **No per-resource region on ACK's S3 controller.** Unlike knr-ops's
  Upbound-flavored resources (each of which carries its own `region`
  field), a single ACK `s3-controller` install targets one AWS region via
  its own controller config. The cross-region replica bucket in
  `prod/s3-bucket.yaml` uses S3's `createBucketConfiguration.
  locationConstraint` to land in `us-west-2` instead, which works but is a
  different mechanism than "one resource, one region field" - a second
  region generally needs a second controller install in a real cluster.
- **HTTPS exposure (SPEC AC #6, ALB/CloudFront + ACM) is not implemented
  in this arm**, matching `golden-base/knr-ops`'s own app manifest, which
  also stops at a `ClusterIP` Service with no Ingress/ALB/CloudFront
  object. This arm's `app.yaml` files mirror that scope rather than adding
  HTTPS coverage knr-ops itself lacks; ACK does have `elbv2-controller`
  and `acm-controller` CRDs that could close this gap if/when it's tackled
  for the whole `golden-base/` set, not just `bare`.
